# Met On Campus

Bun workspaces monorepo. Want to help? Read [CONTRIBUTING.md](CONTRIBUTING.md): `main` only takes pull requests, and CI must pass.

| Path | What |
|---|---|
| `apps/web` | TanStack Start (React, Vite, Tailwind v4). Talks to the API through Eden Treaty. |
| `apps/marketing` | Next.js marketing site for metoncampus.xyz (static; see Marketing site). |
| `apps/platform` | Next.js staff monitoring app (see below). |
| `apps/api` | ElysiaJS on Bun: REST + native WebSocket (`/ws`). Exports `type App` for Eden. |
| `packages/db` | Drizzle ORM schema + migrations (PostgreSQL). |

## Run

```sh
cp .env.example .env          # defaults point at local Postgres + Redis
docker compose up -d          # or use your own Postgres/Redis (createdb metoncampus_dev)
bun install
bun run db:migrate
bun run dev                   # web :3000, api :3001
```

Dev sign-in: request a code for any `*.edu.ng` address. With `RESEND_API_KEY` empty the code prints in the API console; set it (plus `EMAIL_FROM` on your verified Resend domain) to send real email. Production refuses to boot without the key.
`bun run db:seed` loads sample students, rooms and chats (sign in as `amina@st.futminna.edu.ng`).

## Marketing site
`apps/marketing` is a static Next.js site for the root domain: home (with an interactive mode preview), safety, universities, terms and privacy. It sets no cookies, loads no analytics, and every call to action points at the app (`NEXT_PUBLIC_APP_URL`). The "Star on GitHub" link (footer and a "Built in the open" band on the home page) is a plain link, not GitHub's button, because that loads a third-party script; the star count is read from GitHub on the server at build time (refreshed at most daily) and shown only from 10 stars up, so visitors never contact GitHub unless they click. The repository URL lives in `apps/marketing/src/lib/site.ts`.

- `/join` is a "scan to join" page for showing people: a large QR code for `NEXT_PUBLIC_APP_URL` (always dark on white, even in dark mode), the typed address, three steps, PNG/SVG downloads for posters and chats, and a print layout. The code is generated at build time in `src/lib/qr.ts`; if the app URL changes, rebuild and redownload the files. It is noindexed and not in the sitemap.
- Local: `bun run dev` (marketing on :3200).
- Env (not secret, baked into the build): `NEXT_PUBLIC_SITE_URL` (default `https://metoncampus.xyz`), `NEXT_PUBLIC_APP_URL` (default `https://app.metoncampus.xyz`), `NEXT_PUBLIC_CONTACT_EMAIL` (defaults to `hello@metoncampus.xyz`, which Cloudflare Email Routing forwards to a personal inbox; set the variable only to override it). If it is ever set to empty, the universities and legal pages say contact details are coming.
- Vercel (new project): Root Directory `apps/marketing`, "Include source files outside of the Root Directory" on. Add the domain `metoncampus.xyz` and redirect `www.metoncampus.xyz` to it.
- The hero photos are from Unsplash (`src/lib/photos.ts`), hotlinked from their CDN with the photographer credit shown on the card, as Unsplash's guidelines require. To swap one, search the Unsplash API, call the photo's `download_location` once when you pick it, and update that file. The CSP allows only `images.unsplash.com` for remote images. The Unsplash key is only needed while choosing photos, so keep it out of the repo (`apps/marketing/.env.local` is gitignored).
- The terms and privacy pages are a plain-language starting point written from how the product works today. Have a Nigerian lawyer review them, and update them (and `updated` in `src/lib/site.ts`) whenever data practices change.

## Platform app (staff monitoring)
`apps/platform` is a separate Next.js app for `platform.metoncampus.xyz`: overview metrics, reports queue with moderation (dismiss / record warning / suspend), student lookup, live activity, campuses (which universities can sign up, and with which student email domains), announcements (push notifications from staff), departments and campus spots, photo review, service health + Railway deployments, and an audit log.

- **No public sign-up.** Staff are created with `bun run admin invite <email>` (prints a one-time, 24h setup link). The address must also be in the API's `PLATFORM_ADMIN_EMAILS`. Login is email + password (argon2id) + authenticator code, with 10 single-use backup codes. 5 failures lock the account for 15 minutes; sessions last 8h, 30 min idle.
- **Staff cannot read private chats.** They see counts, profiles, and the saved snapshot of a *reported* message. Every sign-in, search, profile view and moderation action is written to the audit log.
- **Photo review.** Staff see each pending photo with the student's name, campus and mode, and every approval, rejection and take-down is in the audit log. The platform fetches the image through its own server, so the service token never reaches a browser.
- **Data path.** The platform's server calls `/admin/*` on the API with a shared secret (`ADMIN_API_TOKEN`) plus the staff member's session. The browser never talks to the API from this app, and the database stays private.
- **Departments and campus spots** are managed on the platform (Departments, Campus spots). An entry can be offered to every campus or to one; renaming carries over to every student who has it; entries students still have can be archived (no longer offered) but not deleted. The web app reads its choices from `GET /meta`, and the API checks profile departments, usual spots and meetup spots against the same lists. The migration seeds today's lists plus anything students already use. "Usually free" is a set of preset chips plus an optional note, stored as one comma-separated line (max 160 characters); the presets live in `apps/api/src/lists.ts`.
- **Department requests.** A student whose department is not listed can ask for it (onboarding or Profile: "My department isn't listed"): one open request at a time, three a day, and a name already on the list is refused with a pointer to it. Until it is decided they show as "Department pending" (stored as `Unspecified`, which never counts as "the same department" for Romance's hide-from-my-department). Staff decide on the Departments page: add it as new (this campus or all), map it onto an existing department (for a misspelling), or decline with a reason. Everyone who asked for the same name on a campus is decided together; approving moves anyone still on "Unspecified" onto it, and students are notified live and see the outcome on their profile.
- **Photos.** Each mode has its own optional profile photo, and nothing is shown to anyone else until staff approve it on the platform's Photos page (approve, or reject with a reason the student sees). A replacement waits for review while the current photo stays up; staff can take a live photo down. Romance photos appear only after a match (a Spark the other person accepted), in Discover, in the conversation and at the image URL itself. Uploads are decoded from their real bytes, rotated, cropped square, re-encoded as 640px WebP and stripped of all metadata; JPEG, PNG or WebP up to 6 MB, 5 uploads a day. Images are never public URLs: `GET /photos/:id` checks the viewer on every request (same campus, same mode, not blocked, not suspended) and answers with `Cache-Control: private, max-age=300`, so a block or removal takes effect within minutes. Files live in S3-compatible storage (the Railway bucket `ergonomic-drawer`); without storage settings, dev and tests write to `apps/api/uploads/` (gitignored) and production keeps uploads switched off.
- **Campuses** (`/campuses`, `apps/api/src/campuses.ts`, `admin/campuses.ts`) decide which universities can create accounts. A campus is identified by the part of the email domain right before `.edu.ng` (`st.futminna.edu.ng` is `futminna`). Staff open a campus (optionally starting from a copy of the template department and spot lists), rename it, and pause or resume it; pausing stops new accounts only, students already in keep signing in. Each campus can have up to 5 **student email domains** (`campuses.email_domains`, e.g. `st.futminna.edu.ng`): new accounts must use one of them exactly (`x.st.futminna.edu.ng` does not match), each domain must belong to its campus, and a campus with none set accepts any address at the university. Students already signed up are never locked out, a code requested before a rule changed cannot create an account at a non-matching address, and a refused address is told which domain to use (`email_domain_not_allowed`). The page also lists "asked to join": sign-up attempts from universities that are not open, counted by university only (no email, name or IP). Every change is audited (`campus.open`, `campus.domains`, `campus.pause`, `campus.resume`).
- **Announcements** (`/announcements`, `admin/broadcasts.ts`) send a push notification written by staff (title up to 50 characters, message up to 140, an in-app link) to students who have notifications on: everyone, one campus, or one department. The page shows how many students and devices it reaches and asks for confirmation. Only active students are sent to; links must be in-app paths; an identical announcement within 10 minutes is refused; at most 5 an hour across staff. The announcement is recorded (history, `push_broadcasts`, and the audit log) before it is sent in the background, so large audiences never time out the request; "delivered" fills in afterwards. Unlike automatic notifications it ignores the per-kind throttle and the "already in the app" rule, because there is no in-app copy.
- **Suspending** a student ends their sessions immediately, blocks sign-in, and hides them from Discover, rooms and chats. Restoring is one click.

Local: set `ADMIN_API_TOKEN`, `ADMIN_ENCRYPTION_KEY`, `PLATFORM_ADMIN_EMAILS` in `.env` (see `.env.example`) and the same token in `apps/platform/.env.local`, then `bun run dev` (platform on :3100).

Production:
1. Railway (API): set `ADMIN_API_TOKEN`, `ADMIN_ENCRYPTION_KEY`, `PLATFORM_ADMIN_EMAILS` (they are `preserve()` in `.railway/railway.ts`, so they live only in Railway), then `railway config apply`. The next deploy runs the new migration.
2. Vercel (new project): Root Directory `apps/platform`, "Include source files outside of the Root Directory" on. Env: `ADMIN_API_URL=https://jeer.metoncampus.xyz`, the same `ADMIN_API_TOKEN`, and optionally `RAILWAY_API_TOKEN` / `RAILWAY_PROJECT_ID` / `RAILWAY_ENVIRONMENT_ID` / `RAILWAY_SERVICE_ID` for the deployments panel. Add the domain `platform.metoncampus.xyz`.
3. Create your account: `railway ssh --service @moc/api -- bun apps/api/src/admin/cli.ts invite you@example.com`, open the link, set a password, scan the QR code, save the backup codes.
4. After the first deploy, confirm `/admin/overview` on the API returns 404 without the token, and that the platform's pages send the CSP and `X-Frame-Options` headers.

## Tests
```sh
bun run test:setup                    # once: creates the metoncampus_test database
bun run test                          # API tests: visibility rules, auth + rate limits, blocking/reporting, meetups, rooms
bun run --filter @moc/web test        # student app: fast unit tests for its logic (Vitest)

createdb metoncampus_e2e              # once, for the browser tests
bunx playwright install chromium      # once, from apps/e2e
bun run --filter @moc/e2e test        # real browser, real API and database (Playwright)
```
The API tests run in-process against a real Postgres and Redis (db 15). They truncate tables and flush Redis, so the setup refuses any database whose name doesn't end in `_test`.

The browser tests (`apps/e2e`) start the API, the student app and the platform themselves on ports 3200, 3201 and 3300 (so a running `bun run dev` is not disturbed), against a throwaway database named `..._e2e` and Redis db 13, which `apps/e2e/prepare.ts` empties and refills on every run (it refuses any other database name). They cover the journeys that cross screens and API: signing in with an emailed code and onboarding, the campus student-domain rule, an invite from one student to another, and staff signing in (password plus authenticator code) to open and edit campuses. With no inbox in a test, the sign-in code is read from `GET /dev/outbox/:email`, a development-only route that is never registered in production and answers nothing once an email provider is configured. The staff account, its password and authenticator secret are test-only values in `apps/e2e/env.ts`. The tests also fail on any browser console error, which is how an invalid-HTML hydration warning on Discover was found. When one fails, Playwright keeps a trace and a screenshot in `apps/e2e/test-results`.

CI (`.github/workflows/ci.yml`) runs two jobs on every push and PR: `check` (migrations, web build, typecheck, API tests, web unit tests) and `e2e` (the browser tests, in parallel).

## Deploy
- **API + Postgres + Redis: Railway**, defined in `.railway/railway.ts` (`railway config plan` / `apply`). Custom domains are added with `railway domain`, not in the file's IaC engine. The API listens on `PORT`.
- **Web: Vercel.** The Vite build uses `nitro()`, which emits Vercel's output format when it detects `VERCEL=1`. Without it the deploy builds but every route 404s. Project settings:
  - Root Directory `apps/web`, with "Include source files outside of the Root Directory" on (the app imports the API's types from the workspace).
  - Framework Preset: TanStack Start (or `{ "framework": "tanstack-start" }` in `vercel.json` if detection fails in the monorepo).
  - Env var `VITE_API_URL=https://<api host>`. It is read at build time, so redeploy after changing it.
  - The API's login cookie is `SameSite=Lax`, so the web and API hosts must share a parent domain (`app.` and the API host under the same site), and the API's `WEB_ORIGIN` must equal the web origin exactly.

## Photo storage
The API reads an S3-compatible bucket from `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION` and `S3_VIRTUAL_HOSTED` (all `preserve()` in `.railway/railway.ts`, so the values live only in Railway). Copy them from `railway bucket credentials`; Railway's endpoint works with path-style addressing, so keep `S3_VIRTUAL_HOSTED=false`. The bucket is declared in the config file, because `railway config apply` deletes anything the file does not list. The bucket is in `iad` while the API is in Singapore; if photos feel slow, recreate it in `sin`. Moving to Cloudflare R2 or another provider only means changing these variables.

## Database migrations
Railway runs the committed migrations before every API deploy (`preDeploy: bun run db:migrate` in `.railway/railway.ts`); a failed migration rejects the release and the old one keeps serving. It cannot create them: after changing `packages/db/src/schema.ts`, run `bun run db:generate` and commit the new SQL file and the journal. `bun run db:check` (also run by CI) fails if the schema and the migrations disagree. Local dev does not migrate for you: run `bun run db:migrate` after pulling. Deploys overlap briefly, so keep migrations additive and split anything destructive (drop or rename a column) across two deploys. Drizzle has no down-migrations; undoing a change means a new forward migration or a restore from backup.

## Design decisions
- **Modes never mix.** `intent_profiles` has one row per (user, mode); conversations are unique per (intent, pair) and the inbox API requires `intent`.
- **Romance is mutual opt-in** and honours "hide from my department" on either side (`apps/api/src/visibility.ts`).
- **Invites are answered, not assumed.** The person invited sees Accept / Not now on the Discover card and at the top of the chat. Until they answer, the inviter can send one message. Not now closes the conversation for both, hides it from the person who declined, and keeps the inviter out of their Discover; the inviter just sees it closed. If someone invites you back, you are connected at once. In Romance, an accepted Spark is the "match" that reveals photos.
- **Unread** is per conversation (`conversation_reads`, set when a chat is opened with the tab in view). `GET /me/unread` counts, per mode, chats with unread messages plus unanswered invites; the web app shows it on the Messages tab, each mode tab, each chat and the browser tab title. Pushes over the WebSocket keep it live.
- **Discover** sends a page at a time (`limit`, default 24, max 100) with the `total` and online count for everyone who matches, and supports `q` (name, prompt, bio or tag). The web app keeps your filters and search for the tab session and loads more on request. The API still filters in memory per campus, which is fine for thousands of students; move it into SQL if a campus grows far beyond that.
- **Rewards: streaks, points and friend invites** (`apps/api/src/rewards/`; all four phases done). Opening the app calls `POST /me/checkin`, which counts once per **Nigerian day** (UTC+1) and runs the streak: yesterday continues it, one missed day is forgiven once a week (a "rest day"), anything longer starts again from 1. Points live in an append-only ledger (`point_events`): each award has a unique `(user, key)` so the same thing can never pay twice, per-kind and overall daily caps stop farming (60 a day across the repeatable kinds), and `user_progress.points_total` is always the sum of the un-reversed rows. The rules and their values are in one table, `rewards/rules.ts`, which the Progress page also reads. **Romance never earns points, streak bonuses or invite credit**, by design: the events hook (`rewards/events.ts`) ignores it. Friend invites: every student has `invite_code`; `/login?invite=CODE` is remembered through sign-in, and only a brand-new account is attributed (`referred_by`). The friend counts once they have set up and opened the app on 3 different days; then both get 30 points once, and the inviter's credit stops at 10 friends a month. The invite page never shows the inviter's name. Staff see a student's ledger, streak and inviter on their page and can reverse an award with a written reason (audited; the row stays and its key stays used). Decisions to revisit with real data: the point values, the daily cap, and whether 3 active days is the right bar for an invite. **Badges** (`rewards/badges.ts`, table `user_badges`) recognise real activity: 16 of them in five groups (getting started, connecting, rooms and meetups, streaks, inviting). They pay no points and nothing in Romance can earn one. Each rule is a plain test over "facts" read from the real tables in one query (`factsOf`), so people who did something before badges existed get the badge on their next check-in, with no backfill job. `syncBadges` is idempotent, runs from the same hooks as points and from the daily check-in, announces each new badge once (a generic push, "You earned a new badge", never naming it), and never re-grants one that staff revoked (`POST /admin/users/:id/badges/:badge/revoke`, reason required, audited). **Weekly campus leaderboard** (`rewards/leaderboard.ts`, `GET/PUT /me/leaderboard`, column `user_progress.leaderboard_opt_in`): opt-in and off by default, and only students who joined can see it, so nobody can look without being on it. It lists first name (or "A student" if the name looks like a matric number), level and points, only for the same university, only active accounts, and only points from this Nigerian week (Monday to Sunday). It is read straight from the points ledger, so there is no snapshot to reset and a staff reversal counts immediately. Top 10, plus your own place when you are further down; ties go to whoever got there first. **Privacy and fairness:** blocked people never appear on each other's leaderboard (either direction, and ranks count only whom you can see); deleting an account removes points, streak, badges, check-ins and the leaderboard entry, friends keep what they earned and their `referred_by` link is cleared; staff see who a student invited, with active days and whether each paid out (`rewards.invitees`), as a farming check. **Tuning:** the values in `rules.ts` are starting guesses. `apps/api/src/rewards/review.sql` has five queries to run on real data after a few weeks (where points come from, how often the daily cap bites, the weekly spread, invite conversion, opt-in); change values from those results.
- **Installable app and push notifications.** The web app is a PWA: `public/manifest.webmanifest`, icons in `public/icons/` (regenerate from `favicon.svg` with `bun run icons` in `apps/web`), and `public/sw.js`, a deliberately small service worker that never caches the app or account data. It shows an offline page when a page load fails, receives pushes, and opens the right screen when one is tapped (only same-origin URLs). `sw.js` is served `no-cache` (Nitro route rules in `vite.config.ts`; a cached service worker would never update). Profile has an install card (Chrome/Edge/Android use the browser's install prompt; iPhone gets Share > Add to Home Screen steps) and a dismissible install nudge in the app; the unread count also goes on the app icon where supported.
- **Push** (`apps/api/src/push.ts`): needs a VAPID key pair (`bun run push:keys` in `apps/api`; `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, optional `VAPID_SUBJECT`, and use different pairs for dev and production). Without them push is off and the Profile card is hidden. A device subscribes from Profile (a tap asks the browser; iPhones only allow it from the installed app); `push_subscriptions` holds one row per device, and a device signed into another account moves to that account. Every event published to a person (new invite, message, room news) becomes at most one notification per kind per 2 minutes, only if they are not in the app, with fixed generic text (no names, no messages, no mode). Gone devices (404/410) are deleted. Subscription addresses are only accepted if they are the real browser push services over HTTPS (Google, Mozilla, Apple, Microsoft), because the server sends to them. Account deletion removes the devices, and sign-out forgets this device. The `Topic` header (which lets a newer notification replace an older one of the same kind) is the notification kind encoded as base64url (`pushTopic`): Apple's push service answers `400 BadWebPushTopic` to a plain word such as `broadcast` or `badge`. A refused send logs `[push] refused <status> <service host> <reason>`.
- **Accessibility** (WCAG 2.2 AA is the target). The web app shell has a skip link and a `<main id="main">`; every screen has one `h1` (Messages has a screen-reader-only one); on in-app navigation the title becomes "<Page> · Met On Campus" and focus moves to `main`, because a single-page app never reloads and screen readers would otherwise hear nothing. Keyboard focus shows a 2px ring everywhere (`:focus-visible` in `styles.css`; do not add `outline-none` without a replacement), and when a button is replaced by what it opens (report menu, meetup composer, delete account, room cancel) focus moves into the new content and back on close. Colour tokens used for text must be 4.5:1 on every surface: use `text-ink-2`/`text-ink-3`, `text-live-ink`, `text-warn-ink` (the plain `live`/`warn` colours are for dots and icons only). `prefers-reduced-motion` switches animation and transitions off globally. Audited with axe-core (0 violations on all marketing pages in light and dark and all web screens at 360 and 1200px) plus keyboard tests; staff platform not yet audited.
- **Emails** are Mustache templates (`apps/api/src/mail/`): one shared `layout.html` (table-based with inline styles, a dark-mode variant and a hidden preheader, because email clients need that) and a `<name>.html` + `<name>.txt` pair per email (the text file's first lines are `Subject:` and `Preheader:`). Mustache escapes values for HTML by default, so nothing user-supplied can inject markup. Preview any of them in development at `http://localhost:3001/dev/email/<signin|delete-account|waiting>` (`?text=1` for plain text, `?light=1` to force the light version); that route does not exist in production. Add an email by adding the two template files and one line in `email.ts`.
- **"Something is waiting" alerts** (`apps/api/src/alerts.ts`) are a digest, not one email per event: when an invite, an unread chat or a room update has gone unanswered for 10 minutes (and is under a day old), the person is not in the app, and they have not been emailed in the last 6 hours or about the same news, they get one email with counts. It never names anyone or any mode, so it is safe if someone sees the inbox. Blocked pairs, declined invites, suspended people and closed chats never count. It runs every minute inside the API (`ALERTS_ENABLED`, on by default in production only; a Redis lock keeps several instances from double sending). Each email carries a one-click unsubscribe (`GET /unsubscribe/:token` shows a button, because mail scanners open links; the button and the `List-Unsubscribe-Post` header POST). Students can switch it in Profile. Sign-in and deletion codes are never affected. Needs `PUBLIC_API_URL` for links (defaults to https://jeer.metoncampus.xyz in production).
- **Account deletion** (`apps/api/src/account.ts`) is immediate and permanent. Students do it in the app (Profile, Delete your account): a fresh 6-digit code emailed to their address plus typing DELETE (`POST /me/delete/code`, then `POST /me/delete`; codes live 10 minutes in Redis, 5 tries, one a minute). Staff can do it on request from a student's page on the platform, by typing the student's email and a written reason; suspended students cannot sign in, so this is also the route for them. It removes the profile, photos (files too), chats and the messages in them, requests, blocks, sessions, presence and rooms they host (people with a place or waiting are told). **Reports and moderation records are kept**, with the account link cleared (migration 0008): a report about the person keeps `reported_label` (name and campus), and staff see it as "a deleted account" and can still close it. The audit log records `account.self_delete` or `user.delete` with the id and campus, never the email or name. A crash between the database commit and the file delete could leave an orphaned photo file; there is no sweeper yet.
- **Chats** return the newest 200 messages (oldest first), and a meetup proposal can no longer be answered once its time has passed.
- **Names** are a first name or nickname, letters only (never a matric number). Onboarding asks for it; accounts created before that were named from the email address and get a one-time prompt. An existing name can always be kept, so it never blocks saving other details.
- **"Online now"** means the app is open, not that someone is on campus, and the interface says so. We chose not to geofence presence: it would need device location (the privacy policy promises we do not read it), a boundary per campus, and a permission prompt, for a badge and a count.
- **Meetups** can only be proposed at public campus spots (`CAMPUS_SPOTS`); only the recipient can accept/decline.
- **On Campus Now** lives only in Redis: a per-user key with `EX` (`PRESENCE_TTL_SECONDS`, default 90s) plus a ZSET index for listing. The web app sends a WS `presence` frame every 30s; stop and you expire.
- **Auth limits** (Redis): 1 code/min and 5/hr per address, 20/hr per IP, 15 verify attempts per 15 min per address. Set `TRUST_PROXY=true` only behind a proxy that overwrites `X-Forwarded-For`.
- **Action limits** (`LIMITS` in `apps/api/src/ratelimit.ts`) cap what one signed-in student can do repeatedly, per student and never per IP (whole campuses share one Wi-Fi address). Invites 10 per 10 minutes and 40 a day; messages 30 a minute and 600 an hour; meetup proposals 10 an hour; new rooms 5 an hour and 15 a day; room join requests 20 an hour; joining an online room's call 30 an hour; room edits 20 an hour; Discover 60 a minute; profile edits 30 an hour; check-in 20 an hour; the on-campus heartbeat 30 a minute (over the socket, extra frames are ignored); blocking 60 an hour; and 600 requests a minute across everything signed-in (`authed`). Over a limit the API answers `429 {"error":"too_many_requests","retryAfter":seconds}` with a `Retry-After` header, and the web app shows "You have reached the limit for invites/messages/rooms for now". Fixed windows in Redis; if Redis fails the request is let through and logged, so a limiter hiccup never takes the app down. Reports, photos, push, department requests, account deletion and sign-in keep their own limits.
- **Request log** (`apps/api/src/httplog.ts`): one line per request, `[http] METHOD route status Nms`, so the deploy logs show which routes are called. It logs the matched route pattern (`/unsubscribe/:token`), never the real URL, so tokens, ids and query strings stay out; no headers, cookies, bodies or IPs; unknown paths show as `unmatched`; `/health` is skipped; off under `bun test`.
- **Gender** is optional (male, female, or not set; `users.gender`) and shown as a small icon beside the name on Discover cards, never as a text label. Each mode has its own "show my gender on my cards" switch (`intent_profiles.show_gender`, on by default). When it is unset or hidden the `gender` key is absent from the card JSON, not `null`. It is only returned to its owner on `/me`; `publicSelf` (used for other people in blocks, connections and rooms) deliberately leaves it out. It is never used for matching, filtering or search, and never appears in pushes, emails or logs.
- **Blocking** hides two students from each other everywhere (Discover, rooms, new connections) and freezes any existing chat: hidden, unreadable, unwritable. **Reports** snapshot the reported message so reviewers still see it if it's deleted; staff review them on the platform's Reports page.
- **Online rooms** (voice plus text chat on LiveKit Cloud; `apps/api/src/livekit.ts`, `roomsweep.ts`) are a second kind of Study or Hangout room, with no place. Any student can host one for up to **20 minutes**; **premium** hosts can run up to **4 hours**; guests join free. Premium is a flag on the student (`users.premium_until`): `bun run admin premium <email> <days|off>`. Needs `LIVEKIT_URL`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET`; without them online rooms are unavailable (creating or joining answers an error and the UI says so). Only the host and approved members can join, and only while the room is live (between its start and end). **Voice and chat are never recorded or stored** by us. Blocking applies, without ever revealing a block to the person it was placed on: only the person who placed a block is prompted at the door ("someone you blocked is in this call") and can choose to join anyway or not, and if someone they blocked joins later they get an in-call banner (Leave or Stay). A person who was blocked by someone in the call is never told and joins normally. A block either way between a student and the host means the room does not exist for them (`404`). A sweep runs once a minute (only when LiveKit is configured, and never two passes at once): it closes the call of every online room that ended in the last 15 minutes, and of every cancelled online room until 15 minutes after its original end (so a close that failed at cancel time is retried and an old token cannot reopen it), and removes anyone in a live call who is not an approved member or is suspended. A removed person's join token stays valid until the room ends, so a removal takes effect within about a minute. Joining is limited to 30 an hour per student. The e2e suite uses fake `LIVEKIT_*` values (`apps/e2e/env.ts`) and never connects to LiveKit.
- Room approvals lock the room row so concurrent approvals can't exceed capacity.
- **Rooms are hosted, edited and cancelled by their host.** Editing tells everyone who has a place; spots cannot drop below the people already in. Cancelling keeps the row (`cancelled_at`), hides the room from everyone except people who had a place or were waiting (they see it marked cancelled, as news), and closes it to new requests. Answers and cancellations are "news" until the member opens Rooms (`room_members.decision_seen_at`); hosts are told how many people are waiting. `GET /me/unread` returns a `rooms` count that drives the Rooms tab badge.
- **Profile edits are never lost silently.** Each mode's form stays mounted, so switching tabs keeps what you typed; a mode with unsaved changes gets a dot, and leaving the page asks first.
